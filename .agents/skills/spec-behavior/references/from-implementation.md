# 既存実装から振る舞い仕様を抽出する

## 対象を決める

依頼されたコマンド、API、イベントハンドラなど、実際に使われる入口から処理をたどる。
設定によって経路が変わる場合は対象の設定を明記する。観測する値を先に決める。たとえば、呼び出し元が受け取る結果、保存後に読める状態、外部サービスへの呼び出し順がある。

## 仕様を書き出す

1. 入口から観測点まで、入力、分岐条件、状態更新、結果を拾う。異常終了、例外の伝播、再試行の有無も実装で確かめる。既存テストは、そのうちどの経路をどんな条件で実行したかを調べるために使う。
2. 入力だけで結果が決まる処理は入出力表にする。履歴や外部処理の順序が効く部分には状態機械を使う。二つの実装状態をまとめるときは、以後の同じ入力に対して観測結果を区別する必要があるかを確かめる。
3. Markdownに対象範囲、表またはMermaid図、根拠、未確認事項を書く。表の行や図の遷移をファイルと関数・分岐に対応づける。仕様と異なる既存の要求やテストがあれば、その差を残す。外部システムの保証をソースから確認できない場合は前提として記録する。
4. 状態機械を含む文書は既存の手順で厳格な静的検査にかける。TLCやQuintを使うときは、確かめたい性質を要求から定め、実行した範囲と結果を記録する。入出力表だけの仕様は、表のケースを実装で実行して照合する。

## 実装と照合する

書き出した仕様を固定し、実際の入口を具体的な入力で呼ぶ。観測値と仕様上のイベントや状態との対応を明示する。期待値は固定した表や図から取り、実測値は戻り値、永続状態、外部呼び出しなどから独立に取る。実装に同じ分岐をもう一度書いた観測器は使わない。

正常系と失敗系を実行し、最初に食い違う入力・状態・期待値・実測値を報告する。一致した場合も、試した範囲と外部依存を代替した箇所を示す。実装の変更を検査するときは、照合前に仕様を再生成しない。抽出時から存在する不具合を見つけるには、独立した要求や不変条件を使う。

specforge リポジトリでは `docs/verify-execution.md` に実装から起こした仕様があり、`tests/verify-execution.test.ts` が実際の関数をこの図と照合している。
