# 文書レビューの読者前提と用語契約

この文書は、READMEと関連ドキュメントを同じ読者像と用語で保守するための作業契約である。

## 読者前提

| 項目                           | 内容                                                                                                                                                                                                                   | 根拠                                                                                             | 不確実な点                                                                                             |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 読者の役割                     | READMEと概念文書は、振る舞い仕様と形式検証を初めて知る利用候補者を主な読者とする。書き方と例は、仕様を書いて検査したい利用者を主な読者とする。入力仕様と開発文書は、構文解析と変換処理を変更する保守者を主な読者とする | READMEは利用価値、ビルド、利用手順を説明し、正準文書は概念、執筆、機械的な入力契約を分担している | 利用候補者のプログラミング経験は資料から確定できないため、コマンドラインの基本操作だけを既知と仮定する |
| 読後に行う判断または作業       | 利用候補者は自分の対象に振る舞い仕様が必要か判断する。利用者はMermaidで仕様を書き、静的検査とモデル検査を実行する。保守者は入力契約を壊さずに実装を変更する                                                            | README、`docs/writing-specs.md`、`docs/spec.md`の役割分担                                        | CSPmとFDR4を実際に使う利用者の比率は確認できない                                                       |
| 既知としてよい事項             | Markdown、ファイル、コマンド、イベント、条件、処理の成功と失敗                                                                                                                                                         | 利用手順がGitとDenoの操作を前提としている                                                        | GitやDenoを初めて使う読者まで含むかは確認できない                                                      |
| 説明が必要な事項               | 振る舞い仕様、状態機械、拡張状態機械、静的検査、モデル検査、デッドロック、進行性、公平性、TLA+、TLC、CSPm、FDR4、抽象構文木                                                                                            | これらは本ツール固有または形式手法の専門用語であり、利用価値と検査結果の解釈に必要になる         | なし                                                                                                   |
| 資料にないため確定できない事項 | 想定する組織規模、開発工程、既存のテスト戦略、FDR4を導入する環境                                                                                                                                                       | リポジトリの文書に記載がない                                                                     | 文書では一般化せず、確認できる機能と制約だけを書く                                                     |
| 適切な具体例                   | 決済と在庫確保を並行して進め、決済の無制限な再試行によって処理が終了しない注文処理                                                                                                                                     | READMEと実行可能な二つのサンプルで、静的検査と進行性検査の違いを再現できる                       | この例は実際の決済APIの副作用を表さないため、検査範囲を併記する                                        |
