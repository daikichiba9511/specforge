# 振る舞い仕様とは何か

振る舞い仕様は、システムが「どの状態で、どの出来事を受けると、何をして、次にどの状態へ進むか」を定義する文書である。
この文書では、振る舞い仕様を使う場面、構成要素、仕様と実装の境界、形式検証との関係を説明する。
実際の書き方は[振る舞い仕様の書き方](./writing-specs.md)を参照する。

## 振る舞い仕様が必要になる判断

現在の入力だけで出力が決まる処理は、変換表や入出力例で表しやすい。
一方、過去に起きた出来事や現在の状態によって応答が変わる処理は、状態遷移として表す必要がある。

例えば、注文の取消イベントを考える。
注文前なら何もせず、決済後なら返金し、発送後なら返品手続きへ進むのであれば、イベント名だけでは振る舞いを決められない。
現在の注文状態が必要である。

次の特徴を持つ処理は、振る舞い仕様の対象になりやすい。

- 同じイベントへの応答が状態によって変わる。
- 再試行、取消、タイムアウト、回復がある。
- 複数の処理が独立して進む。
- 正常終了だけでなく、失敗として終了する経路がある。
- 途中で進めなくなる状態や、終了しない循環を調べたい。

## 拡張状態機械

specforgeは、振る舞いを**拡張状態機械**として記述する。
拡張状態機械は、状態と遷移からなる状態機械に、状態変数、ガード、アクションを加えたモデルである。

| 要素       | 意味                                 | 例                                |
| ---------- | ------------------------------------ | --------------------------------- |
| 状態       | 同じイベントへの反応が変わらない期間 | `WaitingPayment`、`Shipping`      |
| イベント   | 状態機械が反応する出来事             | `payment_authorized`、`timeout`   |
| ガード     | 遷移を許可する条件                   | `retry_count < 3`                 |
| アクション | 遷移に伴って行う作用の名前           | `reserve_stock`、`report_failure` |
| 状態変数   | 状態名だけでは表しにくい値           | 残高、再試行回数                  |
| 遷移       | ある状態から別の状態へ移る規則       | 支払待ちから決済中へ進む          |

Mermaidの遷移ラベルは、次の順序で書く。

```text
event [guard] / action
```

例えば、`submit(item_count) [has_items] / accept_submission`は、次の順序で読む。

1. `submit`イベントと`item_count`を受け取る。
2. `has_items`ガードを事前状態で評価する。
3. 条件を満たせば`accept_submission`アクションを行う。
4. 矢印の先の状態へ進む。

詳しい省略規則は[遷移ラベルの読み方](./label-reading.md)で説明する。

## 状態を分ける基準

実装の関数やクラスに合わせて状態を作るのではなく、同じイベントへの反応が変わる境界で状態を分ける。

例えば、`cancel`を受けたときに返金の要否が変わるなら、決済前と決済後は別の状態である。
反対に、内部処理が異なっても受け付けるイベントと外部から見える結果が同じなら、一つの状態として扱える。

状態変数は、残高や再試行回数のように連続的に変わる値を表す。
状態変数を増やすほど、モデル検査器が探索する組合せも増えるため、遷移判断に必要な値だけを残す。

## 完全性とは何か

ここでいう完全性は、現実世界のすべてを仕様へ書くことではない。
仕様が選んだ範囲で、取り得る状態とイベントの組合せに解釈の空白を残さないことである。

各状態について、少なくとも次を確認する。

- どのイベントを受け付けるか。
- ガードが成立しない場合にどうなるか。
- 取消、失敗、タイムアウトをどう扱うか。
- 定義していないイベントを無視するか、エラーにするか。
- 終了状態か、次の遷移が必要な状態か。

送信側が同じイベントを複数回送る可能性も考慮する。
同じ要求を繰り返しても結果が一回分と同じ性質を**冪等性**という。
通知や予約などのアクションについて、重複を許せるのか、重複除去が必要なのかを仕様の設計メモへ残す。

## 階層状態と直交領域

複数の状態に共通する外向きの遷移は、親となる**階層状態**へまとめられる。
例えば、決済中のどの段階からでも取消できるなら、決済処理全体を一つの親状態として表せる。

独立して並行に進む状態は、**直交領域**に分ける。
決済と在庫確保を直交領域にすると、両方が同時に有効で、それぞれが独立した順序で進むことを表現できる。

直交領域は、見た目を横に並べるための機能ではない。 複数の領域が同時に有効になる場合だけに使う。

現在のspecforgeは、直交領域を各領域の遷移が交互に起きるモデルへ変換する。
同名イベントを複数領域へ同時に配送する同期は生成しないため、その同期を必要とする性質は検証範囲外として明記する。

## 複数の主体を扱う場合

注文、決済、在庫のように状態の所有者が異なる場合は、主体ごとに状態機械を分ける。
共有イベントは、発生元、受信先、配送方法、一緒に渡す値をイベント契約表へ書く。

一枚の大きな図へすべてを詰め込むと、誰が状態を所有し、誰がイベントを発生させるのかが曖昧になる。
状態機械を分けても、イベント名と受け渡す値を契約として揃えれば、仕様同士の接点を追跡できる。

## 振る舞い仕様と実装の境界

振る舞い仕様は、外部から観測できる状態変化と、その条件を定義する。
プログラムがその仕様どおりに動くかを証明するものではない。

| 振る舞い仕様に書くもの   | 別の実装文書やテストで扱うもの      |
| ------------------------ | ----------------------------------- |
| 状態、イベント、遷移     | クラス、関数、モジュールの構成      |
| ガードが参照する値と条件 | データベースのスキーマや索引        |
| アクションの目的         | APIやライブラリの具体的な呼び出し方 |
| 重複時に必要な冪等性     | 冪等性を実現する取引IDや保存方式    |
| 共有イベントの契約       | メッセージ基盤の設定や再送処理      |

specforgeは、CSPmではアクション名をイベントとして残すが、TLA+では現在アクションを状態更新として表現しない。
例えば`reserve_stock`というアクションを書いても、TLCは実際に在庫が保存されることや、二回呼んでも一回分の結果になることを証明しない。
このように内部の処理内容を展開しない要素を、形式手法では不透明な要素と呼ぶことがある。

## 形式検証との関係

**モデル検査**は、有限にした状態と遷移の組合せを機械的に探索し、宣言した性質に違反する実行を探す方法である。
specforgeはMermaid図と補助表をTLA+へ変換し、TLCというモデル検査器へ渡す。

現在のspecforgeでは、主に次を調べられる。

- 終了状態ではないのに、どの遷移も選べないデッドロックがあるか。
- 宣言した終端状態へいずれ到達するという進行性に違反する実行があるか。
- 未定義のガード、明らかな未到達状態、出口のない状態などの静的な不整合があるか。

`verified ok`は、次の限定された意味を持つ。

> 指定した有限の値域と公平性の仮定の下で、生成したモデルに宣言済みの性質への反例が見つからなかった。

仕様に書かれていない要求、実装と仕様の一致、アクション内部の副作用は検査されない。
また、現在はアクションによる状態変数の更新、複数ファイルの合成、直交領域の同時イベント同期を生成しない。

したがって、要求の読み合わせ、振る舞い仕様の意味レビュー、specforgeの静的検査、TLCのモデル検査、実装テストは、それぞれ別の役割を持つ。
